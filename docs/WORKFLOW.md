# How threads ship to Tyler's Mac

The one home for merging, reinstalling and parallel work. Project instructions and memory point here.

## Merge as you go
- Tyler has standing approval for a thread to merge its own PR once CI is green (typecheck, tests, build, e2e), without waiting for his review. Flag anything risky first, such as a change to the library's file format.
- Before merging, run `/code-review` on the PR's diff and fix what it confirms. Self-merge has no other reviewer.
- Then merge with `bun run ship --reviewed` from the PR's worktree (`packages/core/scripts/ship.ts`). It brings master in, numbers new decisions and findings and fails on any placeholder left, pushes, refuses while master's last *completed* test run is red (a run cancelled by the next push shows no red, which is how #174's break went unseen until #186), waits for the PR's checks, starts again if master moved meanwhile, squash-merges and pulls `~/Developer/ore`. Merge by hand only when it can't run, and then do those same steps.
- Stacked PRs merge in order, each with master brought in first.

## After a merge: pull, and the app reinstalls
- On the Mac (Remote Control): `git -C ~/Developer/ore pull --ff-only`. With `core.hooksPath .githooks` set, the `post-merge` hook reinstalls /Applications/Ore.app in the background when the pulled commits touch `apps/desktop/`, `packages/` or the root package files, since the app carries an `ore` compiled from them (D30) (log: `~/Library/Caches/ore/app-install.log`). Check the log says `installed`. If Ore is open but not the frontmost app, it is then quit as ⌘Q does and reopened in the background on the new build (`relaunched`); if he is using it (frontmost), it is left alone and runs the old build until he quits it.
- The hooks install only from `master`: commits in a branch worktree never replace the installed app.
- Pause pulls while Tyler or an AI tester is using the app.
- Automatic updates (Tyler, 2026-11-17): a launchd job (`com.tylerpoelking.ore.auto-update`, `apps/desktop/scripts/auto-update.ts`) does the pull above every 15 minutes and at login, so the Mac app follows master without a thread pulling. Each pass skips while the checkout is off master, memory is below 25% or any Codex tester runs; then it fetches, pulls with `--ff-only` (the post-merge hook reinstalls), and, when the iPhone answers over Wi-Fi and the pulled commits touched `apps/`, `packages/` or the root package files, runs `bun run phone:install`. A phone that is away is caught up on a later pass; the commit last built for it is in `~/Library/Caches/ore/phone-built`. Log: `~/Library/Caches/ore/auto-update.log`. `bun run auto-update install` (re)loads it, `uninstall` removes it, `run` does one pass. A phone install quits Ore on the phone if it is open there.

## The Mac session
- A Remote Control session goes offline when the Mac sleeps, and its messages wait until it wakes (2026-11-13: offline 30 min until Tyler wrote). Tyler keeps "Prevent automatic sleeping on power adapter when the display is off" on (System Settings › Battery › Options). When a session comes back after a gap, check `pmset -g log | grep -E "Sleep|Wake"` before blaming anything else.
- Computer use on the Mac: on 2026-11-13 its approval prompt never reached Tyler (denied twice, no prompt shown). Threads now link to his computer with its own computer-use tools (2026-11-20), so ask once when a hands-on pass needs it; if the prompt doesn't reach him, write the pass to `/mnt/project-files/ai-user-testing/` and he runs it himself in Codex or ChatGPT.

## Parallel threads
- `~/Developer/ore` stays on `master`: the installed app carries a CLI compiled from it at install (D30), run against his real library. Build branches in a worktree (`git worktree add ../ore-<topic>`), never by checking one out there.
- Bring `origin/master` in before pushing; `bun run ship` does it again before merging, since another thread may have landed.
- New decisions and findings carry placeholders, `D-new-<slug>` in `docs/DECISIONS.md` and `F-new-<slug>` in `docs/reviews/findings.md`, mentioned by those names everywhere in the branch. `bun run ship` runs `bun run ids` after master is in and commits: each placeholder becomes the next free number. Open PRs never claim the same number, and `.gitattributes` (`merge=union`) keeps both sides' new rows in a rebase; the decisions and findings tests catch a duplicate. A run on master fails on any placeholder left there (`bun packages/core/scripts/ids.ts --check`), since one breaks `bun run ids` for every other branch: whoever sees it red names it first.
- Git housekeeping is the thread's job, never Tyler's: do resets, rebases, branch cleanup and reinstalls yourself on the Mac, and never ask him to run a git command. Never rewrite master's history; if it ever must be, the thread that does it also resets `~/Developer/ore`, rebases open PRs and deletes the old branches.
- Name files in NFC Unicode (macOS shows NFD names as untracked).

## Mac load
Five Codex testers at once, each with its own WebKit pages, servers and bridges, froze Tyler's Mac until it restarted (2026-11-15). Three at once held (2026-11-26: 25% free at the lowest, warning pressure for six minutes, never critical; `docs/reviews/2026-11-26-simulated-learner-3x/`), so Tyler set the limit at three, started apart. Reopen it if a run of three goes below 25% free or reaches critical. So:
- Before writing a sweep's prompts, read `docs/reviews/sweeps.md` (every tester so far, its angle and how many real bugs it found, and the ground not yet covered) and pick angles from there; when its triage is done, add a row per tester and strike the ground it took.
- Run a Codex sweep with `bun run sweep <folder>` from a worktree. The folder holds `sweep.json` (each tester's name and seed), an optional `preamble.md` and a `<name>-prompt.md` per tester, written with `{{mac}}`, `{{bridge}}`, `{{phone}}`, `{{webkit}}`, `{{library}}`, `{{phoneLibrary}}` and `{{out}}` for this run's ports and folders (the header of `apps/desktop/scripts/sweep.ts`; `--dry-run` prints the plan). It runs at most three testers, each two minutes after the last so the load check sees what the one before took, a library bigger than the big seed alone, starts each only when the load check passes, never uses a port WebKit refuses, and stops everything it started when it ends or is stopped.
- Anything else that loads the Mac (Playwright, a test instance of Ore, a hand-run tester) runs `bun apps/desktop/scripts/mac-load.ts check` before each start and waits while it fails (below 25% free memory, or three Codex testers already running across all threads), and `mac-load.ts clean <worktree>` when it ends or fails. Clean never stops Tyler's own Ore, `~/Developer/ore` or a Claude session.

## Component catalogs (shadcn MCP)
- `.mcp.json` starts the shadcn MCP server (`bunx --bun shadcn@latest mcp`, no key) in Claude Code sessions on this repo. Approve it once when Claude Code asks; check with `/mcp`.
- It searches the registries in the root `components.json`: shadcn/ui (always on), Cult UI (`@cult-ui`, MIT) and Rare UI (`@rare-ui`). Ask by registry, e.g. "show me `@cult-ui/…`"; a bare name searches only shadcn.
- Rare UI is MIT plus a Commons Clause that bars redistributing its components, which clashes with D120: read it for ideas, never copy its code into Ore. shadcn and Cult UI code may be copied in, restyled to `DESIGN.md`.
- The root `components.json` holds only registries, so `shadcn add` won't write files from it; bring a component in by reading it through the MCP and adapting it by hand.
