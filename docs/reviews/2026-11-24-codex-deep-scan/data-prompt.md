
# Your run: data (scheduling, the files on disk, two devices)

Your name is `data`. Your folder is `{{out}}/`. Your seeded library is `{{library}}` (the phone's copy: `{{phoneLibrary}}`). Budget: about 60 minutes. Mostly core and CLI; use the pages only to show what a learner would see.

Hunt in this order, building a red loop for each suspicion. The files to read are starting points, not limits.

1. **Review scheduling is a pure function of the review logs.** `packages/core/src/scheduler.ts`, `queue.ts`, `reviews.ts`, `cards.ts`, D21, D22, D24, SPEC §3. Fuzz: random sequences of `ore review` ratings over pinned clocks (days, months, DST changes, a clock set back), then rebuild every card's state by replaying `reviews/*.jsonl` from scratch and compare with what the card files and `ore today --json` say. Due dates, stability, lapses, the order of the queue, new exercises per day, buried or suspended exercises, a card edited or deleted after it was reviewed, a variant (D66) reviewed in place of its card.
2. **Two devices on one library.** Logs are per device (`reviews/<yyyy>-<mm>.<device>.jsonl`, `ORE_DEVICE`). Run two `ore` processes with different `ORE_DEVICE` on one library, interleaved and truly concurrent: both review the same card the same minute, one archives or deletes a source the other reviews or notes, both edit one note, both rename one skill. Then add what iCloud does: a conflicted copy (`note 2.md`, `2026-11.mac 2.jsonl`), a file that arrives half-written or late, a log that arrives after the card it touches was deleted. Does every review count once, does every merge keep both sides, does any write land on a stale read (`lock.ts`)?
3. **The index is disposable.** `.index` must be rebuildable from the files alone (CLAUDE.md rule). Delete `.index` at random points (mid-session, after outside edits) and diff every `--json` listing, count and level before and after (`db.ts`, `stats.ts`, `skills.ts`, `today.ts`). Also edit files outside Ore (frontmatter by hand, a card file removed, a source folder renamed in Finder) and see whether the index notices.
4. **Frontmatter and file round-trips.** `frontmatter.ts`, `cards.ts`, `notes.ts`, `annotations.ts`: fuzz values (colons, quotes, `---` lines, YAML keywords like `no`/`on`/`null`, dates, emoji, RTL, very long lines, CRLF, a BOM) through write, read, write again; the second write must equal the first and lose nothing.
5. **Recovery from the library's git history** (`history.ts`, D5): snapshots taken while a write is half done, a restore of one note or source, then what `ore` and the Mac page show afterwards.
6. **AI stamps** (CLAUDE.md: every AI output records vendor, model, prompt version): with `ORE_AI` and `ORE_AI_MODEL` switched between writes, check every file an AI path writes carries the right stamp. Use the mock or a stub script; never run real AI.
