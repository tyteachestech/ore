# Your run: snapshot (what the history holds, and what it can't give back)

Your name is `snapshot`. Read `packages/core/src/history.ts` and every caller, then prove:
1. **What is in a snapshot.** Walk every kind of file a library holds (SPEC's layout, `library-agents.md`) and say which are committed, which are gitignored (`.index/`, `.ore/`: cuts, queue files, open session, logs) and whether anything Tyler would want back lives only in a gitignored place (a cut's removed text, a queued link or file, a draft answer, phone-only data).
2. **When it snapshots.** Ten minutes from the last snapshot, from any command; the app's writes on the Mac go through `ore`, the iPhone's through `phone/core.ts` in-process (does the phone ever snapshot? It has no git: what does history hold for a change made on the phone and synced by iCloud?). A day where Tyler only uses the app: how many snapshots, and can a change of five minutes ago be got back? A write out under the lock (the `tryWithLock` path): does the next command snapshot it, or can a write slip past every snapshot?
3. **Git states an agent can leave.** Detached HEAD after `git checkout <sha>`, a stash, a stopped rebase, `index.lock` left by a killed git, a repo with no commits, a library whose `.git` is a file (worktree) or missing, git not on PATH (the app's own compiled `ore`, D30, and its PATH on macOS). Each: does `snapshot` fail quietly forever, commit onto the wrong ref, or break the command (it must never fail one)?
4. **Size and time.** Recordings, PDFs and videos committed each time they change; `git add -A` on a 950-source library (the bench seed, `bun run bench` is off limits: build a smaller one and extrapolate); does any command wait on git while the lock is held?
