# Ore decisions (settled 2026-10-09)

Outcome of a two-round design interview. Each line is a decision, not a suggestion. Change one only with Tyler's explicit say-so, and record the change here.

## Purpose
- D1. Optimize for *explaining concepts in my own words* and *applying them in my work*, not fact recall. Primary review unit is an open-ended prompt graded against a rubric. Atomic cards exist for facts and terms, secondary.
- D2. Standalone product. No engram (Tyler never used it; it felt awkward). Hard break from NotionRPG: no Notion, no shared schema. Ideas only, filtered through the evidence brief.
- D3. Mac first. Phone later only if free. Never trade Mac UX for portability. (Amended 2026-10-27: a full iPhone app is being built alongside, D78.)
- D4. Personal tool, single user, local only, no accounts, no sync, no API keys. (Amended 2026-10-27: sync between his Mac and iPhone is planned, D78; still no user API keys.) (Amended 2026-11-06: Ore is open source, D120; the old ban on AGPL/GPL dependencies is lifted on the Mac.)

## Data
- D5. Files are canonical, in a library folder outside the code repo (default `~/Ore`), under local git, not pushed anywhere. SQLite under `.index/` is a rebuildable index. iCloud only after a phone client exists. (2026-10-27: the phone client exists and the files are laid out for two devices, D78.)
- D6. Agents (Claude Code, Codex) read and write the library directly, guided by the library `AGENTS.md`, and use the `ore` CLI for anything with invariants (IDs, review log, anchoring). MCP server later, as a thin CLI wrapper, only if a chat app without a shell needs it.

## AI
- D7. AI runs through the `claude` and `codex` CLIs on Tyler's subscriptions. No in-app API calls. One adapter so the vendor is swappable.
- D8. Deterministic work (ingest, transcripts, indexing, scheduling) runs in the app or CLI with no model. AI enrichment (prequestions, skill and topic tags, card drafts, topic merges, FSRS optimizer) runs immediately on capture in the background, with a nightly idempotent catch-up as a Claude Code Desktop scheduled task. Design for "runs when awake, catches up once".
- D9. Err toward trusting AI for convenience. Drafts go live without an approval inbox; Tyler fixes mistakes on the fly (edit the card, or chat about it). Never describe AI generation as learning.

## Stack
- D10. Tauri 2 shell. TypeScript core on Bun, shared by the CLI and the app. React UI. One FSRS implementation: ts-fsrs (FSRS-6, defaults until ~1,000 reviews, optimizer via the native binding, run monthly).
- D11. Native needs that Tauri lacks (read selected text from another app via Accessibility; later, screenshot OCR via Vision) are tiny standalone Swift CLI helpers compiled with `swiftc`. No Xcode project.
- D12. Build order: core + CLI (v0) → Claude skill + Raycast extension (v0) → Tauri app (v1). Nothing in v0 is thrown away.

## Learning loop
- D18. Prequestions: on capture, AI writes 2–4 broad questions on the document's central ideas. Shown at the top of the reader, one-line answers or "no idea", stored, unscored. Re-asked closed-book when finishing the source (text hidden), followed by a short free recall ("anything else you remember?"), then AI feedback. Feedback always comes after the attempt. After the recall, one optional line asks "Where would you use this, and what does it connect to?" (Adler and Ahrens; practitioner-backed, not evidence-backed; replaced "use or dispute" 2026-10-23). The finish and chapter feedback also says in one line whether his section lines (D32) state main ideas in his own words (2026-10-23). EPUBs also get a short closed-book recall with AI feedback at each chapter marker; the book end keeps the full finish (both 2026-10-22). The finish and chapter recalls accept typed free recall or a map drawn from memory (D35), never both in one recall (2026-10-23).
- D19. Two review item kinds, both FSRS-scheduled: `card` (atomic Q/A or cloze, facts and terms) and `prompt` (open-ended explain/apply, 2–4 rubric points). Only Card-intent highlights, My notes (D31), maps (D35) and, after the finish, the prequestions produce items; items drafted from My notes are credited "from your notes" (2026-10-22), and items drafted from relationships drawn in a map "from your map" (2026-10-23). Each prequestion becomes a `prompt` (rubric from the document and the ideas he missed) so central ideas get spaced retrieval (2026-10-23). Keep/Question/Research never do by themselves. (2026-10-28, as D91 records: a Keep with a note is also drafted from when the note marks a key point to remember, prompt `enrich`; Research is gone.)
- D20. Card finishing: AI drafts from every Card-intent highlight. The draft's first appearance in review is the finishing step: answer cold → see AI draft answer → edit if needed → live. No approval queue.
- D21. Grading: confidence tap before reveal; Tyler types an answer; AI grades against the rubric and proposes a rating 1–4; one key accepts, any other overrides. Tyler's rating is what FSRS records. A miss triggers one relearn pass in the same session. (Amended 2026-10-24: Fact cards are flipped, not typed, D59.) (Amended 2026-11-11, Tyler: Review's key bar names the rating ↵ accepts as its button does, "↵ Hard", never "↵ Suggested".)
- D22. Skill priority never touches FSRS math or reorders by importance alone. Priority maps to desired retention (P1 0.92, P2 0.88, P3 0.80, lowered from 0.95/0.90/0.85 on 2026-10-25, D65; a card takes the max of its skills) and breaks ties in the daily queue under overload.
- D23. No quota, no streaks, no XP, no daily cap. Review is open-ended; an optional 10-minute time box is a later UI option. Display fairly basic stats at the skill level (items read, items live, reviews, retention using the Anki-adapted metric; never show a trend arrow at small n). Track session starts. (Amended 2026-10-24: a daily time goal and a new-card limit, D60; motivation rules, D62.)
- D24. Interleave topics; place confusable concepts adjacent; keep definitions grouped by source. Vary application prompts rather than rewording cards. (Built 2026-10-25 as remixed cards, D66.)
- D25. Skills (owned by Tyler, 9): AI P1, Learning P1, Teaching P1, Storytelling & Writing P2, Creator Business P2, Creativity P2, Habits P3, Focus & Attention P3, Self-Regulation & Motivation P3. Topics are AI-created and AI-merged. Enrich assigns only skills that obviously fit and never stretches one; when none does, it records a `suggested_skill` on the item, shown as a dashed chip. One click creates it (P2) and files the item, its cards and topics under it; AI never creates a skill itself (2026-10-22).

## Maps (2026-10-23)
Evidence and rationale: `docs/research/brief-diagramming.md`. Deferred (D95): basics first. Diagrams in notes (D40) are built.
- D35. Each source can have one **map**: a freehand whiteboard drawing (Excalidraw, MIT; tldraw excluded for its license key), stored as `map.excalidraw` beside `notes.md`, fonts bundled, no network.
  1. It starts from memory: at the finish and chapter recalls he chooses typed recall or a map, never both (D18). Mapping with the text open lost to plain recall, and a map before a recall added nothing.
  2. After that it is his, like My notes (D31): editable any time with the source open, hidden during recalls (D34.4), no AI drawing or text in it (D34.2).
  3. After his attempt, AI shows its own map beside his with comparison prompts ("what does it have that yours lacks? which link differs?") and names missing ideas and wrong links. It never edits his map or sets a rating (D21, D34.3).
  4. Relationships he drew can seed `prompt` items credited "from your map" (D19).
  5. No map gallery or map-review screen (D34.1). Stats report retention for items from map recalls vs typed recalls, null below 10 reviews (D34.8).
  6. Freehand was chosen over typed boxes and arrows although an on-screen drawing tool erased drawing's benefit in one study (d = 0.87 on paper vs −0.16; F&M ch04). Retention (item 5) decides whether it stays.
  7. Deferred: a cross-source map (D33), a compare-and-contrast matrix.

- D121. **PDF cleanup rules, scored on 15 PDFs** (Tyler, 2026-11-06). ## How an exercise is written (2026-11-10, Tyler: "Yes to your recommended exercise types/process above", after `docs/research/brief-exercise-types.md`)
- D182. **One process for every exercise, rules for each type, and fill in the blank only for exact things** (amends D19's "atomic Q/A or cloze"; refines D66, D118, D147 and D158). Evidence and grades for every line: `docs/research/brief-exercise-types.md`.
  1. **The process.** The AI that writes an exercise works in this order: decide what he should be able to do with the idea (recall it exactly, explain it, use it), and let the type follow; write the answer and its key points from the source before the question; one target; words the source did not use, standing alone.   2. **The types Ore writes.** **Fact** (a term, name, number or single fact; never a list, a yes/no, or a question that holds its answer). **Fill in the blank**, a Fact written as a statement (below). **Explain** (a specific why or how, never "Explain X"). **Apply** (stored as Explain: a setting from his work the source did not use, a decision or product asked for, a key point tied to the setting, answerable from the source's idea alone; a central idea gets a Fact for its definition and an Apply, since use need not wait for the facts). The changed versions of D66 (new case, predict, find the mistake, choose and justify, name it from a case) each carry how to write them and what to avoid. The tutor's Practice kinds (D128, D158), figure labels (D166), prequestions, the finish recall and goal tries stay as they are. Not added: multiple choice (a candidate for the iPhone, where typing is slow) and order the steps (a candidate once procedures and code matter more); each would be mocked first.
  3. **Fill in the blank.** Only when exact wording is the point: a term inside its definition, a number, a name, a command or piece of syntax, one part of a formula. A fresh, complete statement, never the source's sentence, with that one thing written `____`; the answer is what it hides; exactly one answer fits. Never a blank for a reason, a mechanism or a step. Core sends a draft back (`blankProblem`) when it has more than one blank, a blank plus a question, a blank in an Explain exercise, or an answer over five words.
  4. **A blank shows as `____`** (a bug this found). The prompt used to ask for Anki's `{{c1::word}}`, and nothing hid it: review showed the question as written, answer included.   6. **Checked by the question eval** (`docs/guides/question-eval.md`): `code:lifted` fails a question that shares eight words in a row with its source (a blank is read with its word back in), and the judge's `blank_fits` fails a blank that hides a reason, an unimportant word, or one several words could replace. The tutor eval passed 32 of 32 and the grading eval 20 of 20.
  Why: what he can do afterwards follows what the exercise asked. Practising a fact strengthens that fact and did not lift questions that need the idea used (Agarwal 2019); a different case each time is what builds use (Butler 2017). Fill in the blank helped the blanked item and little else (Hinze & Wiley 2011; Tran et al. 2015), and a lifted sentence can be completed from its shape. Format matters less than what is retrieved and whether he is corrected, so the types Ore has stay and the rules for writing them tighten.
